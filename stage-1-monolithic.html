01 / 起源

一切是怎么开始的

在计算机出现的最初几十年里，没有人谈论"架构"。工程师们只是把代码堆在一起，就像把所有家具塞进一个房间——不是因为这样最好，而是因为当时根本没有别的选择。

要理解单体架构为什么诞生，我们必须回到一个更根本的问题：为什么人们需要计算机？ 答案并不浪漫——是为了算账。二战后，银行和航空公司每天需要处理海量交易：存款、取款、航班预订、库存盘点。这些工作以前由成百上千的会计和文员用笔和纸完成，错误率高、速度慢、成本高得惊人。

"我们不是在做软件，我们是在做一个能自动算账的机器。" —— 1960 年代某 IBM 工程师的口头禅

关键转折点发生在 1964 年。 IBM 推出了 System/360 系列大型机——这是计算机历史上第一个"兼容系列"，意味着企业可以买不同型号，但它们运行相同的软件。这大大降低了企业使用计算机的门槛。银行、航空公司、保险公司蜂拥而上。但有一个问题：这些机器贵得离谱——一台大型机的价格相当于今天数百万美元，而且体积大到需要专门建一个恒温恒湿的机房。

当时的现实约束

1960–1990 年代的工程师面临三重枷锁：硬件极其昂贵（一台机器一栋楼的钱）、网络几乎不存在（ARPANET 1969 年才诞生，且仅供学术研究）、编程语言极其原始（COBOL 和 Fortran 是主流，没有"模块化"的概念）。在这样的环境下，"把所有东西放在一起"不是选择，而是必然。

那么，科学认知发生了怎样的变化？在早期（1940s–1950s），人们认为"程序 = 计算任务"——写一段代码，输入数据，得到结果，完事。但随着企业开始使用计算机处理日常业务，人们意识到程序需要持续运行、保存数据、支持多个用户同时使用。这个认知转变催生了"系统"的概念——程序不再是用完即弃的工具，而是长期运行的业务基础设施。

为什么是单体而不是别的方向？因为分布式在当时是不可想象的。没有网络，机器之间无法通信；没有标准化协议，不同机器甚至无法交换数据。"把所有代码放在一个包里"是当时唯一能让系统跑起来的方式。这不是最优解，而是唯一可行解。

关键事件时间线

  • 1951 UNIVAC I 成为第一台商用计算机，美国人口普查局用它处理人口数据——软件架构的概念尚未诞生
  • 1964 IBM System/360 发布，企业级计算正式起步。所有程序共享同一台机器、同一个数据库。
  • 1969 ARPANET 诞生，但仅限学术研究。企业界的网络互联还要再等 20 年。
  • 1970 Edgar Codd 提出关系型数据库理论——数据终于有了"结构化"的存放方式，但仍然集中在一台机器上。
  • 1979 Oracle 发布首个商业 SQL 数据库，企业数据管理进入新阶段——但依然是单体。
  • 1981 IBM PC 发布，个人计算机时代开启，但企业核心系统仍运行在大型机上。
02 / 人物

那个时代的人，在干什么

想象一下：没有 Slack，没有 Jira，没有 Figma，甚至没有"产品经理"这个职位。那个时代的人是如何工作的？

老张 · 系统架构师

1960s – 1980s / 大型机时代
每天早上，老张穿上白大褂走进恒温机房——温度严格控制在 20°C，湿度 50%。他的"编程"是把 COBOL 代码写在纸上，然后交给穿孔卡片操作员，操作员把代码转成一叠卡片。老张把卡片塞进读卡机，等上几小时甚至一整夜，才能看到运行结果。如果出错了，整个过程重来一次。他的日常不是"写代码"，而是等代码。最让他焦虑的不是 bug，而是"今晚的批处理能不能在第二天早上 8 点前跑完"——因为银行开门前，所有账目必须对平。

小李 · 业务系统分析师

1970s – 1990s / 最接近"产品经理"的岗位
小李的工位上堆满了纸质流程图和需求规格说明书。没有原型工具，他用铅笔在方格纸上画界面草图，用流程图符号（菱形代表判断，矩形代表处理）描述业务逻辑。他要做的不是"用户体验设计"，而是把银行柜员的日常工作翻译成程序员能懂的规则。例如："当客户存款超过 5000 美元时，系统必须记录交易来源"——这样的规则要写成几十页的技术文档。小李最痛苦的是：写完文档交给开发团队后，要等三个月才能看到第一个可运行的版本。

王姐 · 银行柜员

1980s – 1990s / 终端用户
王姐面前的屏幕是绿色的，纯文本，没有鼠标。她每天的工作是记住几十条指令：输入 ACCT 12345 查询账户，输入 DEP 500 存入 500 元。屏幕上看不到"余额"两个字，只有一行数字。如果系统宕机了，整个银行网点停摆——因为所有数据都在市中心机房的那台大型机上，网点终端只是"远程显示器"。王姐不知道什么是"架构"，但她知道：早上 9 点前系统必须好使，否则几百个客户会在大厅里排队骂街。
"那时候没有'上线'这个说法。系统安装好了，就不会轻易改动——改一次的风险比建一座桥还高。" —— 一位 1980 年代银行 IT 主管的回忆
03 / 产品

那个时代诞生了什么

单体架构时代并非荒芜——恰恰相反，它奠定了现代数字世界的基石。以下是那个时代最具影响力的产品。

IBM System/360

1964 · 大型机

第一个兼容系列商用计算机，让不同规模的企业都能用上同一套软件生态。相当于"计算机界的乐高"——你可以买小号的，也可以买大号的，但它们的零件能互相配合。

SABRE 订票系统

1960 · 航空预订

美国航空与 IBM 合作开发的全球首个实时预订系统。它让旅行社能在几秒钟内查到航班座位，彻底改变了航空业。这个系统今天仍在运行，经过无数次改造。

Oracle Database

1979 · 数据库

首个商业化的关系型数据库。它让数据不再是程序里的附属品，而是独立的、可结构化查询的资产。这是单体架构中"数据层"概念的起点。

SAP R/2

1979 · 企业资源计划

德国 SAP 公司的早期 ERP 系统，运行在 IBM 大型机上。它将财务、库存、生产、销售全部塞进一个系统——这是单体架构的极致体现：一个系统管一切。

dBase

1980 · 桌面数据库

个人计算机上最早的流行数据库软件。虽然它不是企业级大型机系统，但它让普通企业也能在 PC 上管理数据——C/S 架构的雏形开始浮现。

VisiCalc

1979 · 电子表格

世界上第一个电子表格软件，运行在 Apple II 上。它让非技术人员也能"编程"——用单元格公式处理数据。这是"软件民主化"的第一步。

04 / 认知

那个时代的人，心里在想什么

理解一个时代的架构，必须先理解那个时代的人是怎么想的。心理学上，这叫"心智模型"。

认知一：计算机 = 超级计算器

大多数人把计算机看作一个"自动化工具"——它替代了人工记账、人工查表、人工计算。没有人把它看作一个"平台"或"生态"。这种认知直接导致了单体架构的必然性：既然只是一个工具，那把功能塞在一起就好了。

认知二：集中 = 安全

在那个时代，"所有数据在一个地方"被认为是优势而非风险。数据集中意味着容易备份、容易审计、容易控制。分布式在当时听起来像"把金库拆成碎片藏在不同的地方"——令人不安。

认知三：改动 = 危险

修改代码需要重新编译整个系统，重新部署，重新测试——周期以周甚至月计算。因此，"能不动就不动"成为行业信条。这种恐惧心理直接抑制了架构拆分的尝试：拆分意味着更多的改动点，更多的风险。

认知四：软件 < 硬件

当时硬件成本占总成本的 70% 以上，软件只是"让硬件跑起来的配套品"。没有人认为软件本身有独立的价值。这种认知导致软件设计被硬件约束绑架——怎么省钱怎么来，而不是怎么好用怎么来。

"我们今天觉得'所有东西放在一起'很荒谬，但在当时，'分开'才是荒谬的——因为没有网络，分开就等于失联。" —— 软件史学家 Martin Campbell-Kelly
05 / 关键词

关键词词典

每个时代都有它的语言。要真正理解单体架构时代，你必须先学会那个时代的关键词——不只是定义，还有它们之间的关联。

KEYWORD 01

单体架构
Monolithic Architecture

所有功能模块（界面、业务逻辑、数据访问）被写进同一个代码库，部署时作为一个整体运行。想象一家餐厅，厨师、服务员、收银员全是一个人——简单，但没法扩展。

KEYWORD 02

大型机
Mainframe

专为企业级计算设计的巨型计算机，价格昂贵、体积庞大、需要专门机房。特点是高可靠性和高并发处理能力。今天的 ATM 交易、航班预订背后仍有大型机在支撑。

KEYWORD 03

批处理
Batch Processing

不实时处理请求，而是把一堆任务攒起来，等到夜里统一跑一遍。就像快递：不是每收到一个包裹就送一次，而是攒满一车再出发。优点是效率高，缺点是用户得等到第二天才能看到结果。

KEYWORD 04

穿孔卡片
Punch Card

早期程序员把代码写在纸上，操作员用打孔机在卡片上打孔（不同孔位代表不同指令），然后把卡片塞进读卡机。一张卡片 80 列，最多写一行代码。调试 bug 意味着重新打一堆卡片。

KEYWORD 05

终端
Terminal

一台只负责显示和输入的设备，本身没有计算能力。所有计算都在远处的大型机上完成。相当于今天的"远程桌面"——你看到的是画面，但大脑（CPU）在别处。

KEYWORD 06

COBOL
Common Business-Oriented Language

专门为商业数据处理设计的编程语言，语法接近英语（ADD A TO B）。直到今天，全球仍有数十亿行 COBOL 代码在运行——主要是银行核心系统，因为"能跑就不要动"。

KEYWORD 07

关系型数据库
Relational Database

把数据组织成"表"的结构，表与表之间通过"关系"（外键）连接。就像 Excel 的多张工作表，但更加严格和强大。Oracle、MySQL、PostgreSQL 都属于这一类。

KEYWORD 08

C/S 架构
Client-Server

把应用拆成两部分：客户端（Client，负责显示界面）和服务器（Server，负责处理数据）。注意：C/S 不是单体架构的对立面——早期的 C/S 应用中，服务器端仍然是一个单体。

关键词之间的联系

  • 大型机 → 需要 → 终端 → 输入 → 穿孔卡片 / 键盘 → 运行 → 批处理
  • 单体架构 → 运行在 → 大型机 → 用 → COBOL → 操作 → 关系型数据库
  • C/S 架构 → 服务器端仍然是 → 单体架构 → 只是把 → 界面层 → 拆到了客户端 →
  • 批处理 → 因为 → 大型机 太贵，不能闲置，所以夜里也要跑任务 →

易混淆概念辨析

概念对比
单体架构

所有代码在一个包里。关注的是代码怎么组织。

分层架构

代码逻辑上分成了表示层、业务层、数据层，但物理上还是部署在一起。是单体内部的进一步组织。

大型机

一种专用硬件，为企业级计算设计。昂贵、可靠、专有生态。

服务器

一种通用硬件，可以运行各种软件。便宜、标准化、开放生态。

C/S 架构

一种连接方式：客户端请求，服务器响应。关注的是谁和谁通信。

单体架构

一种代码组织方式：所有功能在一个包里。C/S 架构的服务器端完全可以是单体。

06 / 课程

如果穿越回去，该学什么

以下课程不是为了让你成为 COBOL 程序员，而是为了让你理解"计算机是怎么从算盘变成今天的样子"。作为产品经理，你需要的是历史视野，不是编码技能。

01

CS50: Introduction to Computer Science

Harvard University · David J. Malan · 免费

哈佛最著名的计算机导论课。从二进制到 C 语言，从算法到 Web 开发，用极度通俗易懂的方式告诉你"计算机到底在干什么"。作为产品经理，你只需要看前 6 讲（到 Web 开发之前）。

YouTube / edX
02

Code: The Hidden Language of Computer Hardware and Software

Charles Petzold · 书籍 · 通俗科普

从零开始讲计算机的诞生：从摩尔斯电码到继电器，从逻辑门到 CPU，从汇编到高级语言。不需要任何技术背景，就像读一本历史小说。读完你会真正理解"为什么最早的计算机是单体"。

纸质书 / Kindle
03

计算机科学速成课（Crash Course Computer Science）

Carrie Anne Philbin · YouTube · 40集 × 10分钟

用最短的篇幅讲完计算机科学全貌：硬件、软件、网络、AI……每集 10 分钟，像追剧一样学计算机。强烈建议产品经理通刷一遍——建立完整的知识地图，以后和技术团队对话不再心虚。

YouTube / B站字幕版
04

Building Modern Business Applications

Microsoft Learn · 免费 · 面向业务人员

微软官方课程，教你用低代码平台（Power Platform）搭建业务应用。虽然不直接讲架构历史，但它让你体会到：今天的"单体思维"仍然存在——很多业务系统依然是一个大包。
